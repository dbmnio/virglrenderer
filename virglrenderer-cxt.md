# Virglrenderer Codebase Documentation

This document provides a detailed and concise overview of the `virglrenderer` codebase. It is intended to be a guide for developers and AI coding agents to navigate the repository, understand its architecture, and implement new features.

## 1. High-Level Architecture

`virglrenderer` is a library that implements a virtual graphics processing unit (GPU) for guest operating systems running within a virtual machine (VM). It translates graphics commands from the guest's VirtIO-GPU driver into native graphics calls on the host machine. This allows guest operating systems to have hardware-accelerated 3D rendering capabilities without requiring direct access to the host's GPU hardware.

The primary user of `virglrenderer` is a virtual machine monitor (VMM) like QEMU. The VMM acts as a client to the `virglrenderer` library, forwarding command streams from the guest and managing resources and synchronization.

### 1.1. Core Concepts

The architecture is built around a few core concepts:

*   **Resources**: These are GPU objects like textures, buffers, and shaders. `virglrenderer` manages the lifecycle of these resources, including their creation, data mapping, and destruction. It supports zero-copy mechanisms like DMABUF for efficient data sharing between the guest and host.
*   **Contexts**: A context represents a guest application's rendering state (e.g., an OpenGL context). All rendering commands are submitted within a specific context.
*   **Command Buffers**: These are streams of drawing and state-manipulation commands generated by the guest's graphics driver. `virglrenderer` receives these buffers, decodes them, and translates them into corresponding calls for the host's native graphics API.
*   **Fences**: Fences are synchronization primitives used to signal the completion of rendering operations. This allows the guest and host to operate asynchronously, improving performance.

## 2. Core API (`virglrenderer.h`)

The public API, defined in `src/virglrenderer.h`, serves as the interface between the VMM and the `virglrenderer` library. It is designed to be backend-agnostic, allowing the VMM to operate without knowledge of the underlying host graphics API.

The implementation in `src/virglrenderer.c` acts as a central dispatcher. It maintains a global state and tables for resources and contexts. When an API function is called, it looks up the relevant context and forwards the request to the backend associated with that context's capability set (e.g., `VIRTGPU_DRM_CAPSET_VIRGL` for the Virgl backend, `VIRTGPU_DRM_CAPSET_VENUS` for Venus).

### 2.1. Initialization and Configuration

Initialization is performed by `virgl_renderer_init`. This function is critical as it establishes the connection between the VMM and the renderer and configures the operational mode.

*   **`flags`**: A bitmask that controls major features:
    *   `VIRGL_RENDERER_USE_EGL` / `VIRGL_RENDERER_USE_GLX`: Select the host windowing system interface.
    *   `VIRGL_RENDERER_USE_GLES`: Use OpenGL ES instead of desktop OpenGL.
    *   `VIRGL_RENDERER_VENUS`: Enable the Venus (Vulkan) backend.
    *   `VIRGL_RENDERER_RENDER_SERVER`: Offload rendering to a separate sandboxed process.
    *   `VIRGL_RENDERER_USE_EXTERNAL_BLOB`: Enable zero-copy resource sharing via external file descriptors.
*   **`virgl_renderer_callbacks`**: A struct of function pointers provided by the VMM. This is a key design feature, allowing `virglrenderer` to delegate host-specific operations (like creating an OpenGL context or managing fences) back to the VMM. This decouples the renderer from the specifics of the VMM's display and event loop integration.

### 2.2. Resource Management

Resources represent all guest GPU data.

*   **Creation**: Resources are created with `virgl_renderer_resource_create`. The `virgl_renderer_resource_create_args` struct defines the resource's properties (target, format, size, etc.). Internally, this is dispatched to `vrend_renderer_resource_create` for the Virgl backend.
*   **Data Transfer**:
    *   `virgl_renderer_resource_attach_iov` links a resource to guest memory regions described by an array of `iovec`s. This is the primary way data is associated with a resource.
    *   `virgl_renderer_transfer_read_iov` and `virgl_renderer_transfer_write_iov` are used for explicit data transfers between the resource and guest memory (e.g., texture uploads, pixel readbacks). These are dispatched to the context's `transfer_3d` method.
*   **Zero-Copy Sharing**: To avoid costly memory copies, `virglrenderer` supports creating resources from externally managed memory using file descriptors (e.g., DMABUF).
    *   `virgl_renderer_resource_create_blob` and `virgl_renderer_resource_import_blob` are used for this purpose. These are handled by the context's `get_blob` method.

### 2.3. Command Submission and Synchronization

*   **`virgl_renderer_submit_cmd`**: This is the workhorse function. The VMM calls it to submit a command buffer from the guest. The renderer decodes this buffer and executes the commands on the appropriate backend via the context's `submit_cmd` method.
*   **Fences**:
    *   `virgl_renderer_create_fence` creates a fence object. This is typically dispatched to `vrend_renderer_create_ctx0_fence`.
    *   The VMM can either poll for completion using `virgl_renderer_poll` or get a pollable file descriptor via `virgl_renderer_get_poll_fd` for asynchronous waiting.
    *   When a fence completes, the `write_fence` callback (provided during initialization) is invoked to notify the VMM.

## 3. Backend Architectures

`virglrenderer` supports multiple rendering backends, which are chosen at runtime based on the guest's requests and the host's capabilities.

### 3.1. Virgl (OpenGL) Backend (`src/vrend/`)

The Virgl backend is the original and most mature backend. It translates guest OpenGL commands into host OpenGL or OpenGL ES calls.

#### 3.1.1. Core Components

*   **`vrend_renderer.c`**: This is the heart of the Virgl backend. It manages the global renderer state, including OpenGL features and contexts. It handles the creation and lifecycle of all OpenGL objects, such as textures, shaders, and framebuffers.
*   **`vrend_decode.c`**: This component is responsible for decoding the command buffers received from the guest. It parses the command stream and calls the appropriate functions in `vrend_renderer.c` to execute the commands.
*   **`vrend_shader.c`**: This file handles the translation of guest shader code (in TGSI, the Tungsten Graphics Shader Infrastructure format) into GLSL, the shading language used by the host's OpenGL driver. It also manages shader variants and linking.
*   **`vrend_winsys.c`**: This acts as an abstraction layer for the windowing system. It has platform-specific implementations for EGL (`vrend_winsys_egl.c`), GLX (`vrend_winsys_glx.c`), and GBM (`vrend_winsys_gbm.c`), allowing `virglrenderer` to run on different display systems.
*   **`vrend_blitter.c`**: This component provides a "blitter" for performing optimized data transfers and resource copies (blits) using OpenGL.

#### 3.1.2. Data Structures

The Virgl backend uses several key data structures to manage the graphics state:

*   **`vrend_context`**: Represents a guest OpenGL context. It contains sub-contexts (`vrend_sub_context`) which hold the actual OpenGL state (e.g., bound shaders, framebuffers, vertex buffers).
*   **`vrend_resource`**: A wrapper around a `pipe_resource` that represents a generic graphics resource. It is specialized into `vrend_texture` for texture resources.
*   **`vrend_shader_selector`**: Manages different variants of a shader, allowing the backend to recompile shaders with different keys based on the current state.

#### 3.1.3. Execution Flow

1.  A command buffer is received by `virgl_renderer_submit_cmd` and passed to the Virgl backend.
2.  `vrend_decode_ctx_submit_cmd` in `vrend_decode.c` iterates through the command buffer.
3.  For each command, `vrend_decode.c` calls a corresponding function in `vrend_renderer.c` (e.g., `vrend_draw_vbo` for a drawing command, `vrend_set_framebuffer_state` to change the render target).
4.  `vrend_renderer.c` updates the internal state of the `vrend_context` and makes the necessary OpenGL calls to reflect the guest's requests.
5.  If a shader needs to be bound, `vrend_shader.c` is used to select or create a suitable GLSL variant, which is then compiled and linked into a GLSL program.

### 3.2. Venus (Vulkan) Backend (`src/venus/`)

The Venus backend translates guest Vulkan commands into native Vulkan calls on the host. It is a newer and more complex backend, designed to support the full Vulkan API.

#### 3.2.1. Core Components

*   **`vkr_renderer.c`**: This is the main entry point for the Venus backend. It manages the global state and a list of `vkr_context` objects.
*   **`vkr_context.c`**: Represents a guest Vulkan context. It manages the connection to the Vulkan driver and handles resource creation and command submission.
*   **`venus-protocol/`**: This directory contains the protocol definition for communication between the guest and host for the Venus backend. It defines the structures and commands used to serialize Vulkan calls.
*   **`vkr_*.c` files**: These files map to specific Vulkan concepts and objects, such as `vkr_instance.c`, `vkr_device.c`, `vkr_queue.c`, and `vkr_command_buffer.c`. Each file is responsible for managing its corresponding Vulkan object type.

#### 3.2.2. Data Structures

*   **`vkr_context`**: Manages the state of a guest Vulkan context, including the Vulkan instance and device.
*   **`vkr_resource`**: Represents a Vulkan resource, such as a buffer or an image.
*   **Command Stream (`cs`)**: The Venus backend uses a command stream (`vkr_cs.c`) to batch commands for submission to the Vulkan driver.

#### 3.2.3. Execution Flow

1.  A command buffer is submitted via `virgl_renderer_submit_cmd` and dispatched to `vkr_renderer_submit_cmd`.
2.  The command is then passed to `vkr_context_submit_cmd`, which records the command in the context's command stream.
3.  When the command stream is flushed (e.g., when a fence is submitted), the batched commands are submitted to the host's Vulkan driver for execution.
4.  Resources are managed through `vkr_renderer_create_resource` and `vkr_renderer_import_resource`, which handle the creation and mapping of Vulkan memory.

### 3.3. DRM Backend (`src/drm/`)

The DRM backend provides a way to directly interact with the host's Direct Rendering Manager (DRM) subsystem. This backend is used for features that require direct access to the kernel's graphics interfaces, such as zero-copy buffer sharing.

#### 3.3.1. Architecture

The DRM backend is designed as a factory for creating hardware-specific contexts. It has a list of supported backends (e.g., `amdgpu`, `msm`), and it probes the system to find a matching DRM device.

*   **`drm_renderer.c`**: This file contains the main entry point for the DRM backend. `drm_renderer_init` iterates through the available hardware-specific backends and probes for a compatible device. Once a device is found, `drm_renderer_create` is used to create a hardware-specific `virgl_context`.
*   **Hardware-Specific Implementations**: The `src/drm/amdgpu/` and `src/drm/msm/` directories contain the implementations for AMD and Qualcomm GPUs, respectively. These implementations handle the specifics of interacting with their corresponding kernel drivers.
*   **`drm-uapi/`**: This directory contains the userspace API headers for the DRM subsystem, which define the ioctl commands and data structures used to communicate with the kernel drivers.

## 4. Helper Modules

In addition to the core backends, `virglrenderer` uses several helper modules to provide common functionality.

### 4.1. Gallium/Mesa (`src/gallium/` and `src/mesa/`)

`virglrenderer` leverages several components from the Mesa 3D graphics library.

*   **Gallium**: This is a graphics API abstraction layer that provides a common interface for different graphics drivers. `virglrenderer` uses Gallium's helper libraries for tasks like shader translation (TGSI) and format handling.
*   **Mesa Utilities**: The `src/mesa/util/` directory contains various utility functions from Mesa, such as memory management (`ralloc`), data structures (`hash_table`, `list`), and platform-specific OS abstractions.

### 4.2. Proxy and Server Infrastructure (`src/proxy/` and `server/`)

To improve security and stability, `virglrenderer` supports offloading rendering to a separate, sandboxed process.

*   **`src/proxy/`**: This directory contains the client-side implementation of the render server proxy. It marshals commands and sends them to the render server via a socket.
*   **`server/`**: This directory contains the server-side implementation. It receives commands from the proxy, unmarshals them, and calls the appropriate `virglrenderer` functions to execute them. This allows the main VMM process to run with fewer privileges, as the actual rendering is handled by the sandboxed server process.
